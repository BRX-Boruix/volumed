# volumed

BORUIX 的**卷管理守护进程**：自动发现磁盘并挂载，拔盘时自动卸载。

[English](README.en.md)

## 它做什么

```
[volumed] mounted sata-disk-0 -> /volumes/BORUIX_DATA
[volumed] unmounted sata-disk-0 (/volumes/BORUIX_DATA) via probe
```

| 情况 | 行为 |
| --- | --- |
| 出现新的块设备 | 挂载到 `/volumes/{卷标}` |
| 设备消失 | 卸载对应的挂载点 |

## 事件驱动，不做轮询

本进程向内核登记等待设备事件。**事件队列为空时，内核把它挂起**——不占 CPU，也不反复询问"有变化
吗"。设备注册或拔除时，内核唤醒它。

## 周期性对账（兜底）

事件机制不能只靠它。设想一块盘**被拔掉但事件没送达**——挂载点会一直留着，指向一个已不存在的
设备，访问它就会卡住或报错，且看起来毫无原因。

所以还有一个对账兜底：定期醒来检查已挂载的卷是否还活着。这个检查必须**足够轻**——早期版本会真的
去读设备，触发硬件层面的等待，结果是**每隔一个对账周期系统就卡一下**。改成只读几次设备状态后，
操作变为微秒级，卡顿消失。

**间隔取 5 秒**：对账只是兜底，正常情况靠事件驱动就够了。较 1 秒少 5 倍系统调用开销，同时把兜底
发现的最坏延迟控制在 5 秒内。

## 挂载是幂等的

本进程会被反复唤醒，所以挂载必须可以安全重复执行。依靠内核的幂等语义：设备**已挂载**时再挂一次
返回"已存在"，本进程静默跳过。

这避免了重复卷的产生。重复卷一旦出现就很难清理——靠名字后缀判断哪个是真的，是脆弱的启发式：
**真实的卷标如果恰好以 `-N` 结尾，就会被误判**。

## 卸载用真实路径

挂载成功后内核会**回传实际使用的路径**（可能因重名而带后缀）。本进程记录并据此卸载。自己拼路径
（假设一定是 `/volumes/{卷标}`）会在发生重名消解时**卸载错误的位置**。

## 构建

```bash
cargo build --release
```

由系统初始化进程在启动时拉起，之后常驻运行。

## 文件结构

```
volumed/
├── Cargo.toml    # 包定义
├── build.rs      # 注入链接脚本
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 挂载编排与事件循环
```
